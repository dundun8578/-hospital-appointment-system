## 🔍 性能瓶颈分析

### 常见性能问题

#### 1. 响应时间过长（>200ms）

**可能原因**：
- 数据库慢查询
- Redis网络延迟
- MQ消息发送阻塞
- 分布式锁竞争

**排查方法**：
```bash
# 开启慢查询日志
SET GLOBAL slow_query_log = 'ON';
SET GLOBAL long_query_time = 0.1;

# 查看慢查询
SELECT * FROM mysql.slow_log WHERE start_time > NOW() - INTERVAL 1 HOUR;

# 查看Redis延迟
redis-cli --latency -h localhost -p 6379
```

**优化方案**：
- 添加联合索引
- 增加本地缓存
- 优化Redis Key设计
- 调整连接池参数

---

#### 2. 成功率低（<99%）

**可能原因**：
- 超卖（库存扣减失败）
- 重复预约（数据库唯一索引冲突）
- Redis连接超时
- MQ消息发送失败

**排查方法**：
```bash
# 查看错误日志
grep "ERROR" logs/hospital-appointment.log | tail -100

# 查看数据库警告
SHOW WARNINGS;

# 查看Redis连接数
redis-cli INFO clients
```

**优化方案**：
- 增加重试机制
- 优化分布式锁等待时间
- 增加Redis连接池大小
- MQ消息持久化

---

#### 3. QPS低（<100）

**可能原因**：
- 数据库连接池不足
- Redis连接池不足
- 线程池配置不合理
- 同步阻塞操作过多

**优化方案**：
```yaml
# 数据库连接池调优
spring:
  datasource:
    hikari:
      maximum-pool-size: 20
      minimum-idle: 5
      connection-timeout: 30000

# Redis连接池调优
  data:
    redis:
      lettuce:
        pool:
          max-active: 20
          max-idle: 10
          min-idle: 5
```

## 📈 优化方案

### 优化1：添加联合索引

```sql
-- appointment表：用户+排班查询
CREATE INDEX idx_user_schedule ON appointment(user_id, schedule_id, status);

-- schedule表：按日期+状态查询
CREATE INDEX idx_work_date_status ON schedule(work_date, status, available_count);

-- user表：手机号+状态登录
CREATE INDEX idx_phone_status ON user(phone, status);

-- doctor表：科室+状态查询
CREATE INDEX idx_dept_status ON doctor(department_id, status);
```

### 优化2：增加本地缓存

```java
// 使用Caffeine缓存热点数据
@Cacheable(value = "schedule", key = "#scheduleId", cacheManager = "caffeineCacheManager")
public ScheduleVO getScheduleDetail(Long scheduleId) {
    return baseMapper.selectScheduleDetail(scheduleId);
}
```

### 优化3：数据库读写分离

```yaml
spring:
  datasource:
    dynamic:
      primary: master
      datasource:
        master:
          url: jdbc:mysql://localhost:3306/hospital_appointment
        slave:
          url: jdbc:mysql://localhost:3307/hospital_appointment
          driver-class-name: com.mysql.cj.jdbc.Driver
```

### 优化4：Redis优化

```bash
# 开启Redis内存优化
redis-cli CONFIG SET maxmemory 512mb
redis-cli CONFIG SET maxmemory-policy allkeys-lru

# 开启RDB持久化
redis-cli CONFIG SET save "900 1 300 10 60 10000"
```

**现象**：Redis Lua脚本执行时间>10ms

**排查**：

**优化**：

- 调整Redis配置：`save ""`（关闭RDB）
- 使用Redis Pipeline批量操作

---

### 问题2：MQ消息堆积

**现象**：队列中消息数>10000

**排查**：
```bash

# 查看消费者数量
rabbitmqctl list_consumers
```

**优化**：
- 增加消费者并发数
- 增加prefetchCount
- 优化消费逻辑（减少DB操作）

---

### 面试亮点

1. **为什么使用Redis？**
   - 预扣库存，解决超卖问题
   - 高性能（<5ms）
   - 原子操作（Lua脚本）

2. **为什么使用Lua？**
   - Redis单线程执行Lua，保证原子性
   - 避免"先查后改"的并发问题
   - 性能优于多条Redis命令

3. **为什么使用MQ？**
   - 异步削峰，降低DB压力
   - 解耦预约和订单创建
   - 提高系统吞吐量

4. **为什么不用数据库锁？**
   - 数据库锁性能差（行锁开销大）
   - 分布式场景下数据库锁失效
   - Redis/Redisson性能更高

5. **如何保证最终一致性？**
   - 数据库唯一索引兜底
   - MQ重试机制
   - 死信队列人工处理
